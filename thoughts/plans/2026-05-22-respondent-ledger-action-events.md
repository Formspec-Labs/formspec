# Respondent Ledger Action Event Taxonomy

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Steps use `- [ ]` syntax.

**Goal:** Publish four optional event kinds (`action.invoked`, `action.failed`, `action.deferred`, `action.replayed`) on the Respondent Ledger so Response Actions invocations can be audit-trailed without inventing event taxonomy in the Response Actions companion. Reuses existing `response.submit-attempted`, `response.completed`, `draft.saved` for the lifecycle moments those already own. Closes BLOCKER B1 / MAJOR 3 from the Response Actions plan reviews.

**Architecture:** Strictly additive to `specs/audit/respondent-ledger-spec.md` §8 (event taxonomy) and `schemas/respondent-ledger-event.schema.json` (`$defs.EventType` enum + new conditional `allOf` clause keyed on the four new kinds). New `$defs.ActionEventPayload` shape carries the invocation lineage (`actionId`, `invocationId`, `attempt`, `terminal`, `effectIndex`, `causeRef`). No changes to required events, existing payloads, integrity profile, sequence semantics, hash chain. Per Ledger spec §3 design goals: optional add-on, processor-pluggable.

**Tech Stack:** JSON Schema 2020-12, Markdown (W3C-style, BCP-14), `npm run docs:generate`, pytest under `formspec/tests/conformance/`.

**Sequencing:** Schema enum + payload $def first → spec §8 prose append → conformance fixture additions → pytest. The Response Actions plan depends on this landing; this plan is a precondition for that plan.

**Citations:** "Ledger §" = `specs/audit/respondent-ledger-spec.md`. "RA plan" = the Response Actions plan named above.

### Explicitly NOT in scope

- **Materiality of action events.** Per Ledger §8.3 / §8.4 these are optional events; processors MAY choose not to emit them. This plan does NOT force action lifecycle events into the required-kinds set.
- **Trellis integrity binding for the action payload.** Ledger spec already pins hash-chain and integrity profile uniformly; the new payload inherits those semantics without change.
- **Lifecycle ordering rules** (e.g., "action.failed MUST follow action.invoked"). Ordering is observable from `sequence`; spec-level ordering rules are deferred until a real consumer demands them.
- **`case.created` / case lifecycle.** Out of scope per RA-plan §1.4.1 and Ledger §3.2.

## Self-Review Note

- The four new kinds are OPTIONAL. Ledger §3.2 lists non-goals for the spec and §8.2 uses `MAY` for existing optional kinds; this plan extends the optional set without changing the required-event commitment surface.
- Payload binding (`$defs/ActionEventPayload`) lives on the event itself, not in `changes`. Rationale is positive (action lifecycle is not a field-edit), NOT a precedent claim. Earlier draft text claimed a mirror with `validation.snapshot-recorded` — incorrect. The existing schema has no allOf clause for `validation.snapshot-recorded`. The §8.5 prohibition on `changes` for `action.*` is a NEW conformance rule, intentionally introduced.
- The `terminal` enum on `ActionEventPayload` is restricted to `{failed, deferred, replayed}` — the only values the four published kinds emit. The `completed` lifecycle moment is covered by existing `response.completed`; `blocked` manifests via `action.failed` with `causeRef` discriminator.
- `causeRef` / `replayTokenRef` / `priorInvocationRef` are semantically opaque to the Ledger but their BYTE encoding is constrained (ASCII-printable pattern + maxLength) so Trellis canonical event hash construction (trellis-core.md §22.2) is deterministic across deployments. The Response Actions runtime owns the semantic content; this spec owns the encoding.
- The RA-plan fixture set will use these kinds; failure to land this plan first blocks RA-plan Task 13–15 fixture authoring.

## Task 3: Append §8.5 "Action lifecycle events" to the Ledger spec

**Files:**
- Modify: `specs/audit/respondent-ledger-spec.md`

- [ ] **Step 1: Insert §8.5 after §8.4**

Locate the end of §8 (just before §9, or whichever section follows the existing kind catalog). Append:

```markdown
### 8.5 Action lifecycle events

The Respondent Ledger optionally records Response Actions invocation lifecycle. The four event kinds are OPTIONAL — processors that do not implement the Response Actions companion (`specs/response-actions/response-actions-spec.md`) MUST NOT emit them, and processors that do MAY choose which moments to record.

| Event kind | Emitted when | Required payload fields |
|---|---|---|
| `action.invoked` | A Response Actions invocation enters `invoking` state (after snapshot, before preconditions). | `actionId`, `invocationId`, `attempt` |
| `action.failed` | An invocation terminates in `failed`. | `actionId`, `invocationId`, `terminal: "failed"`, `effectIndex` (when an effect caused the failure), `causeRef` |
| `action.deferred` | An invocation terminates in `deferred`. | `actionId`, `invocationId`, `terminal: "deferred"`, `replayTokenRef`, optionally `effectIndex` |
| `action.replayed` | A replay re-enters with a prior invocationId and short-circuits durable effects via the idempotency contract. | `actionId`, `invocationId`, `terminal: "replayed"`, `priorInvocationRef` |

`actionEvent` is the payload binding. Schema enforces presence on each `action.*` kind and forbids `changes`. Rationale: action lifecycle is not a field edit. Field-level material changes from a successful invocation are owned by the kind the action ultimately triggered — typically `draft.saved`, `response.submit-attempted`, `response.completed`, or `attachment.added`. This is a NEW conformance rule introduced by §8.5; it does not mirror any existing event-type clause. Earlier draft text claimed a mirror with `validation.snapshot-recorded` — that claim was incorrect (`validation.snapshot-recorded` has no conditional clause in the existing schema) and has been retracted.

Each of the four `action.*` kinds is independently optional. A processor MAY emit any subset (e.g., `action.invoked` + `action.failed` only, skipping `action.deferred` and `action.replayed` when those paths are not exercised).

**Canonical encoding for `*Ref` fields.** `causeRef`, `replayTokenRef`, and `priorInvocationRef` carry semantically opaque references owned by the runtime. The Ledger does NOT interpret their semantic content. However, because these strings enter the canonical event hash preimage (`trellis-core.md` §22.2 routes Ledger event bytes into `CanonicalEventHashPreimage`), their byte encoding MUST be deterministic across deployments. The schema enforces this via:

- ASCII-printable pattern restriction (excludes Unicode normalization ambiguity entirely)
- maxLength bound (excludes unbounded payload inflation)

A Trellis verifier consuming an exported chain treats these fields as canonical UTF-8 byte strings; the schema-side encoding constraint makes that stranger-test viable without requiring the verifier to consult the Response Actions spec to interpret the payload.

`priorInvocationRef` is **invocation-scoped only**. A processor that reuses this field as a case-continuation handle, response-continuation pointer, or session reference is non-conforming. The Ledger spec §3.2 non-goal forbidding `case.*` event families applies transitively.

**Ordering.** Action lifecycle events appear in the ledger's normal `sequence` order. This spec does NOT impose `action.invoked` MUST precede `action.failed` ordering rules — processors that coalesce or skip the `action.invoked` event are conformant. Consumers that need a guaranteed-paired event view MUST reconstruct it from `invocationId`.

**Relationship to existing kinds.** A successful submit invocation produces a single `response.submit-attempted` (and, on success, `response.completed`) per existing §8 semantics. A processor MAY also emit `action.invoked` to capture the named invocation lineage. The two kinds carry different information; they are NOT substitutes.
```

## Out-of-scope reminders

- **Do not add `action.*` to the required kinds list.** Ledger §3.2 non-goal explicitly forbids forcing adoption of every kind.
- **Do not encode replay-token shape.** The runtime owns its token; Ledger stores the reference.
- **Do not add ordering invariants** ("action.failed MUST follow action.invoked"). `sequence` already orders events; consumers reconstruct invocation views by `invocationId`.
- **Do not define a "case.*" kind family.** Forbidden by RA-plan §1.4.1 / Ledger §3.2.
