# Bundle Manifest Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Spec authoring tasks SHOULD also invoke the `formspec-companion-authoring` skill for prose/schema conventions.

**Goal:** Land the Bundle Manifest spec, schema, and conformance fixtures. Resolves §11.5 of [`thoughts/specs/2026-05-20-formspec-semantic-layers.md`](../specs/2026-05-20-formspec-semantic-layers.md) and records §8 MVB coverage closeout.

**Architecture:** Bundle Manifest is a **top-level primary artifact**, peer to Definition / Experience / Component / Response Actions / Theme / Locale / Mapping / References / Ontology / Registry. It is a pure composition envelope: one Bundle = one form identity = a coherent published-version pin of Definition (required) plus optional siblings (each referenced once by URL+version). **No inline sidecars, no synthesis on absence, no shims** — when a sibling is absent, that sibling's existing spec rules govern (e.g., Definition-only bundles render via Definition's existing widget defaults; no fake Experience is synthesized, per concept §6.2's category-error warning). Definition stays core; Bundle is the optional thin envelope above it.

**Tech Stack:** JSON Schema 2020-12 (`schemas/bundle-manifest.schema.json`), Python pytest conformance harness (`tests/conformance/{schemas,spec}/`), existing docs gate (`npm run docs:generate && npm run docs:check`).

**Non-goals (YAGNI):**
- Rust crate, TS types, Python loader implementation — defer until a consumer (renderer/Studio/MCP) actually needs them. Bundle Manifest is a declarative envelope with no business logic; schema validation is sufficient for v1.
- Backwards-compat shim with Definition's existing reference graph — Bundle is forward composition; siblings keep their `targetDefinition` back-references unchanged. Refactor, don't shim (see [[no-shims-refactor]]).
- Bundle versioning of the Bundle Manifest spec itself beyond v1.0. v1.1 etc. can extend members.

## Bundle Manifest shape (design summary, normative source is the schema)

```jsonc
{
  "$formspecBundle": "1.0",
  "version": "1.0.0",                       // SemVer; the bundle's published version
  "id": "https://example.gov/forms/intake-2026", // stable form identity URL
  "name": "intakeApplication",              // optional slug; ^[a-zA-Z][a-zA-Z0-9_-]*$
  "title": "Intake Application",            // optional
  "description": "...",                     // optional

  "definition": {                           // REQUIRED — exactly one
    "url": "https://example.gov/forms/intake/definition",
    "version": "1.2.0"                      // exact SemVer OR range expression
  },

  "experience":      { "url": "...", "version": "..." },  // optional single
  "responseActions": { "url": "...", "version": "..." },  // optional single
  "component":       { "url": "...", "version": "..." },  // optional single
  "theme":           { "url": "...", "version": "..." },  // optional single
  "references":      { "url": "...", "version": "..." },  // optional single
  "ontology":        { "url": "...", "version": "..." },  // optional single
  "registry":        { "url": "...", "version": "..." },  // optional single (option-set / token enrichment)

  "locales": [                              // optional array; one per BCP47 tag
    { "url": "...", "version": "...", "locale": "en-US" },
    { "url": "...", "version": "...", "locale": "es-US" }
  ],
  "mappings": [                             // optional array; one per handle
    { "url": "...", "version": "...", "handle": "applicationPayload" },
    { "url": "...", "version": "...", "handle": "reviewerSummary" }
  ]
}
```

**Excluded from Bundle (runtime/response-scoped or generated):** Response, ValidationReport, Determination Record, Respondent Ledger, Intake Handoff, Trace. These are produced *from* a bundle at runtime; they don't compose one.

**Sibling version field:** A SemVer string (exact: `"1.2.0"`) or range expression (`">=1.0.0 <2.0.0"`, `"^1.0.0"`). Producers SHOULD pin exact versions in published bundles; range expressions are RECOMMENDED for development.

```markdown
## Conventions and Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP 14][rfc2119] [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

JSON syntax and data types are as defined in [RFC 8259]. URI syntax is as defined in [RFC 3986].

Terms defined in the Formspec v1.0 core specification retain their core-specification meanings throughout this document unless explicitly redefined.

Additional terms:

- **Bundle Manifest** -- A JSON document conforming to this specification, identified by `$formspecBundle: "1.0"`. The author-facing single composition envelope above a Formspec form.
- **Sibling reference** -- An entry inside a Bundle Manifest that names one composed artifact by canonical URL and (optional) version pin or range.
- **Definition-only bundle** -- A Bundle Manifest whose sole sibling reference is `definition`. Renders via Definition's existing widget defaults; no Experience or Component is synthesized.

[rfc2119]: https://www.rfc-editor.org/rfc/rfc2119
[RFC 3986]: https://www.rfc-editor.org/rfc/rfc3986
```

```python
from __future__ import annotations

from jsonschema import Draft202012Validator, ValidationError

FIXTURES_DIR = ROOT / "tests" / "conformance" / "fixtures" / "bundle"
BUNDLE_SCHEMA = load_schema("bundle-manifest.schema.json")


def _validator() -> Draft202012Validator:
    return Draft202012Validator(
        BUNDLE_SCHEMA,
        format_checker=Draft202012Validator.FORMAT_CHECKER,
    )


def _fixture_bundle(name: str) -> dict:
    with (FIXTURES_DIR / name).open(encoding="utf-8") as handle:
        return json.load(handle)["bundle"]


class TestBundleManifestSchemaShape:
    def test_schema_is_well_formed(self) -> None:
        Draft202012Validator.check_schema(BUNDLE_SCHEMA)

    def test_required_top_level_properties(self) -> None:
        assert set(BUNDLE_SCHEMA["required"]) == {
            "$formspecBundle",
            "version",
            "id",
            "definition",
        }

    def test_additional_properties_false(self) -> None:
        assert BUNDLE_SCHEMA["additionalProperties"] is False


class TestBundleManifestPositiveFixtures:

        _validator().validate(_fixture_bundle("bundle-definition-only.json"))

        with pytest.raises(ValidationError) as excinfo:
            _validator().validate(_fixture_bundle("invalid-missing-definition.json"))
```

```markdown
The Formspec architecture composes a form from up to ten authored siblings -- Definition, Experience, Response Actions, Component, Theme, Locale, Mapping, References, Ontology, Registry -- plus generated artifacts (Trace) and response-scoped artifacts (Response, Respondent Ledger, ValidationReport, Intake Handoff, Determination Record). - override sibling semantics (sibling versions, sibling identities, and sibling spec rules are unchanged by being named in a bundle),
- replace Definition as the core executable model (Definition stays the source of behavior; bundle is the optional envelope above it).

A Definition without a Bundle Manifest remains a valid Formspec form. The Bundle Manifest is the **opt-in** seam between architectural breadth (many specs) and authoring ergonomics (open one thing).
```

```markdown
Sibling artifacts each carry a `targetDefinition` back-reference naming the Definition they bind to. Bundle Manifest does **not** change that back-reference graph -- it adds a forward-composition graph alongside it.

### 5.1 Forward Composition (Bundle → Siblings)

The bundle's slot-by-slot sibling references compose a form forward. A consumer that holds a Bundle Manifest can resolve every artifact needed to render or process the form without scanning a content addressable store, registry, or filesystem for documents that target a given Definition.

This is the seam Bundle Manifest adds: discovery without reverse-scanning.

### 5.2 Back-Reference Preservation (Sibling → Definition)

Every sibling document continues to carry its own `targetDefinition` (Experience, Component, Response Actions, Theme, Locale, Mapping, References, Ontology). Those back-references are unchanged. Bundle Manifest does NOT consume them; it does NOT supersede them; it does NOT generate them.

A sibling artifact remains independently valid against its own spec without ever appearing in a Bundle Manifest. The reverse-discovery path (load Definition; find siblings whose `targetDefinition.url` matches) MUST continue to work for tools that do not use Bundle Manifest.

### 5.3 Consistency Between Bundle Pin and Back-Reference

When a Bundle Manifest pins a sibling at version V, the loaded sibling document at `siblingRef.url` MUST satisfy two constraints:

1. The sibling document's own `version` MUST be compatible with the bundle's pin (`siblingRef.version`).
2. The sibling document's `targetDefinition.url` MUST equal the bundle's `definition.url`, and the sibling's `targetDefinition.compatibleVersions` MUST accept the bundle's `definition.version`.

A bundle that names a sibling whose back-reference targets a different Definition is a bundle-resolution error.

### 5.4 No Shim Path

This specification does NOT introduce a `definition.bundle` field, a `Bundle.legacyDefinitionOnly` flag, or any backwards-compat alias on existing primary specs. Bundle Manifest is a peer primary artifact; existing artifacts are unchanged. Implementations migrating to Bundle Manifest add bundle files alongside existing reference graphs; they do not modify existing schema shapes.
```
