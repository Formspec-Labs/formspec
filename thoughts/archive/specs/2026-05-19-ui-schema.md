# Formspec Experience, Form Runtime Actions, and Trace Graph Concept

**Date:** 2026-05-19
**Status:** Superseded by [`2026-05-20-formspec-semantic-layers.md`](./2026-05-20-formspec-semantic-layers.md)
**Short names:** FEX, FRA, FTG
**Scope:** This note captures the conceptual approach and ownership boundaries for future Formspec UI, runtime-action, and traceability work.

This is not a normative companion specification. It does not define final JSON Schemas, conformance fixtures, wire-level processing rules, or implementation phases. Those artifacts should be authored separately, using this note as the architectural guide.

---

# 1. Thesis

Formspec should be a **semantic interaction contract for structured workflows**.

A form is often only the visible edge of a larger system. A respondent is trying to complete a task, provide evidence, satisfy policy, trigger validation, sign or attest something, submit data into another system, and leave an auditable trail. Formspec should make those relationships explicit enough that wireframes, prototypes, production UI, validation, submissions, accessibility, agent assistance, tests, and audit evidence can all project from the same structured source.

The goal is not to add a "UI schema" beside the Definition. The goal is to add the missing conceptual layers around the Definition so interaction intent, runtime behavior, concrete presentation, and accountability remain separable but connected.

---

# 2. Data-Driven Wireframing

The purpose of data-driven wireframing is to make a wireframe a **generated projection of structured intent**, not a detached drawing.

Formspec Core already defines a rendering-independent data-collection instrument: fields, groups, computed values, validation rules, conditional logic, repeatable sections, versioning, and structured validation results. Component Documents already define a concrete parallel presentation tree bound to Definition items, where the component tree controls layout and widget selection but cannot override Definition behavior.

The missing bridge is the **wireframe generator**.

```text
Definition + Experience + Form Runtime Actions
  -> generated Component draft
  -> designer/developer refinement
  -> production Component tree
  -> Trace Graph evidence
```

The generator consumes:

```text
Definition
  fields, groups, labels, descriptions, binds, shapes

Experience
  actors, tasks, abstract interaction units, itemRefs, actionRefs

Form Runtime Actions
  runtime actions, submissions, validation modes

Theme
  optional density, tokens, layout defaults
```

It produces a draft Component tree. That Component tree is the concrete editable artifact.

`generation.strategy` is a closed, registered enumeration governed under §11.1 — initial entries such as `unit-to-card`, `unit-to-page`, `unit-to-step`, and `unit-to-panel`. New strategies arrive through Registry-style `x-` extensions, not freeform strings.

## 2.1 Worked Example

Given this Experience unit:

```json
{
  "id": "identity",
  "kind": "data-entry",
  "taskRefs": ["identifyApplicant"],
  "itemRefs": ["applicantName", "dateOfBirth"],
  "actionRefs": ["saveDraft", "continue"],
  "accessibility": {
    "label": "Applicant identity",
    "description": "Information used to identify the applicant."
  }
}
```

and these Definition items:

```json
[
  {
    "key": "applicantName",
    "type": "field",
    "dataType": "string",
    "label": "Full name"
  },
  {
    "key": "dateOfBirth",
    "type": "field",
    "dataType": "date",
    "label": "Date of birth"
  }
]
```

a wireframe generator could produce this Component draft. Property and component names in this example are illustrative until the formal Component and Form Runtime Actions specs define the exact schema:

```json
{
  "$formspecComponent": "1.0",
  "version": "1.0.0",
  "targetDefinition": {
    "url": "https://example.gov/forms/intake",
    "compatibleVersions": ">=1.0.0 <2.0.0"
  },
  "generation": {
    "source": "experience:identity",
    "strategy": "unit-to-card",
    "generatedBy": "formspec-wireframe-generator@0.1.0"
  },
  "tree": {
    "id": "identityCard",
    "component": "Card",
    "unitRef": "identity",
    "taskRefs": ["identifyApplicant"],
    "title": "Applicant identity",
    "description": "Information used to identify the applicant.",
    "children": [
      {
        "id": "applicantNameInput",
        "component": "TextInput",
        "bind": "applicantName",
        "unitRef": "identity"
      },
      {
        "id": "dateOfBirthInput",
        "component": "DatePicker",
        "bind": "dateOfBirth",
        "unitRef": "identity"
      },
      {
        "id": "identityActions",
        "component": "ButtonRow",
        "children": [
          {
            "id": "saveDraftButton",
            "component": "Button",
            "actionRef": "saveDraft",
            "variant": "secondary"
          },
          {
            "id": "continueButton",
            "component": "Button",
            "actionRef": "continue",
            "variant": "primary"
          }
        ]
      }
    ]
  }
}
```

Visible strings in the example are illustrative. In practice, labels resolve at render time through the Locale spec — Component nodes carry references (e.g., a `titleRef` pointing into Locale), not snapshotted prose, so locale fallback continues to work after generation.

This draft can render as a low-fidelity wireframe, an HTML prototype, or a Storybook preview. The important property is that every visible element remains anchored to source semantics:

```text
Card        -> Experience unit
Inputs      -> Definition items
Buttons     -> Form Runtime Actions
Labels      -> Definition or Locale
Validation  -> Definition and Validation Report
```

## 2.2 Round Trip and Regeneration

Designer edits should happen in the Component tree, not by mutating Experience. Experience remains the abstract journey. Component is the editable concrete projection.

When the Definition, Experience, or Form Runtime Actions document changes, regeneration should use a three-way merge:

```text
old generated Component
+ designer-edited Component
+ new generated Component from updated Definition, Experience, and Form Runtime Actions
= merged Component draft
```

Merge rules:

```text
Preserve designer edits when their source anchors still exist.
Regenerate nodes whose source itemRef, actionRef, or unitRef changed.
Mark orphaned components when their bind, actionRef, or unitRef no longer resolves.
Add newly generated fields and actions as pending review.
Never silently delete designer-authored layout without a trace warning.
```

For example, if `dateOfBirth` is renamed to `birthDate` through a proper Definition migration or changelog, the generator updates the binding:

```json
{
  "id": "dateOfBirthInput",
  "bind": "birthDate"
}
```

but preserves designer-authored presentation choices:

```json
{
  "component": "DatePicker",
  "width": "half",
  "helpPlacement": "inline"
}
```

If no migration or changelog explains the rename, the generator emits a review warning instead of guessing:

```text
Component node dateOfBirthInput references missing item dateOfBirth.
Suggested candidate: birthDate.
Review required.
```

## 2.3 AI Authoring Role

This is where AI belongs. The AI should not freehand UI code; it should propose structured artifacts:

```text
Experience units from requirements and policy text
Component drafts from Experience units
Form Runtime Actions drafts from task and action descriptions
Reference bindings from cited policies
Locale strings and accessible descriptions
```

Formspec then validates the artifacts, renders the wireframe, and generates a Trace Graph showing how the UI connects back to data, policy, actions, validation, and evidence.

The AI loop becomes:

```text
draft structured intent
-> generate wireframe
-> validate schemas and references
-> show preview
-> reviewer edits Component or Experience
-> regenerate safely on model changes
```

That is the concrete promise: **wireframes become reviewable, regenerable projections of semantic artifacts**, not disposable drawings that drift from implementation as soon as someone opens a ticket.

# 3. Conceptual Artifacts

This approach introduces three conceptual surfaces and one shared vocabulary constraint.

| Surface | Primary concern |
|---|---|
| **Experience** | User/task/abstract interaction intent |
| **Form Runtime Actions** | Form-scoped runtime actions, submission policy, and effect orchestration |
| **Trace Graph** | Generated relationship index for accountability and impact analysis |

The vocabulary constraint is narrower: future specs should not invent new hash or opaque-reference primitives. They should reuse `stack-common` and `integrity-stack` for stack-wide primitives, and define only the Formspec-domain reference vocabulary they actually need.

These surfaces sit beside existing Formspec artifacts, not above them.

## 3.1 Formspec-owned artifacts

| Existing artifact | Continues to own |
|---|---|
| **Definition** | Data model, item structure, binds, relevance, requiredness, calculations, validation shapes |
| **Component** | Concrete UI tree, widget selection, layout, item binding |
| **Theme** | Visual tokens, density, and presentation defaults |
| **Mapping** | Response-to-external payload transformation |
| **References** | Supporting resources and human/agent context |
| **Registry / Ontology** | Semantic vocabulary, extension governance, and concept bindings |
| **Validation Report** | Validation evidence and findings |
| **Verification Receipt** | Receipt shape and signing profile ([`verification-receipt.schema.json`](../../schemas/verification-receipt.schema.json)) |

## 3.2 Cross-stack artifacts (Formspec contract + Trellis bytes)

These artifacts have split authority. Formspec owns the contract and authored semantics; Trellis Core owns the canonical byte-level admission and verification. A Formspec-side spec that references one of these must point downstream at the Trellis-owned half rather than redefining it.

| Artifact | Formspec owns | Trellis owns |
|---|---|---|
| **Respondent Ledger** | `RespondentLedgerEvent` semantics, Profile A/B/C posture axes ([`audit/respondent-ledger-spec.md`](../../specs/audit/respondent-ledger-spec.md)) | Canonical admission, hash chain, Respondent History Sidecar ([`trellis-core.md` §22](../../../trellis/specs/trellis-core.md), [`trellis-operational-companion.md` §23](../../../trellis/specs/trellis-operational-companion.md)) |
| **Intake Handoff** | Boundary contract + schema ([`intake-handoff.schema.json`](../../schemas/intake-handoff.schema.json)) | Export catalog binding + offline replay ([`trellis-core.md` §18.2](../../../trellis/specs/trellis-core.md), `wos-trellis-verification.md` WOS-TV-007/008/009) |
| **Posture Declaration** | — | Operator declaration document ([`trellis-operational-companion.md` §11](../../../trellis/specs/trellis-operational-companion.md)) |

Posture Declaration is Trellis-owned outright. It appears here only to mark the seam Formspec consumers cross when they read posture facts.

# 4. Ownership Model

The architecture depends on single ownership per concern. A processor should not require authors to duplicate the same semantic fact in multiple source artifacts.

```text
Definition   = executable form model
Experience   = abstract user journey and task intent
Runtime Actions = form-scoped action and submission orchestration
Component    = concrete UI layout and widgets
Theme        = visual presentation rules
Mapping      = external data projection
References   = supporting context and resources
Trace Graph  = generated relationship index
Primitive refs  = Formspec-domain DefinitionRef and TypedRef vocabulary
```

When two artifacts relate, one must own the fact and the other must reference it.

Examples:

| Fact | Owner |
|---|---|
| A field is required | Definition |
| A group of fields serves a user task | Experience |
| A button invokes a runtime action | Component references Form Runtime Actions |
| An action runs a submission | Form Runtime Actions |
| A submission transforms a response into an external payload | Mapping |
| A submitted response produced validation evidence | Validation Report |
| A handoff transferred validated intake evidence to a workflow host | Intake Handoff |
| A UI element, action, mapping, and receipt are related | Trace Graph, generated from sources |

Trace Graph never becomes the source of truth. If a generated edge conflicts with a source artifact, the source artifact wins.

# 5. Experience

Experience captures the human journey through a Formspec Definition.

It answers:

```text
Who is using this form?
What are they trying to accomplish?
Which tasks exist?
Which abstract interaction units group items, concepts, references, and actions?
Which actor, platform, locale, or posture context was this experience designed for?
```

Experience must not define field structure, validation rules, calculation rules, submission payloads, durable events, or concrete layout.

The first named consumer is the Formspec authoring/wireframe loop: AI and Studio-style tools draft Experience units from requirements, the generator projects them into Component drafts, and reviewers edit the concrete Component tree. Experience earns separation from Component only because that flow needs task intent before a concrete layout exists.

Conceptually, an Experience contains:

```text
target Definition
applicability
actors
tasks
abstract interaction units
```

An abstract interaction unit is not a page, card, or component. It is a task-oriented grouping. The same unit might become a web card, a mobile step, a kiosk screen, or a caseworker panel depending on Component and Theme.

Good Experience content:

```text
Task: identify the applicant
Unit: applicant identity
Items: applicantName, dateOfBirth
Concepts: person.fullName, person.birthDate
Actions offered: saveDraft, continue
References: identity-policy
```

Bad Experience content:

```text
Use a two-column card
Render this as a TextInput
Mark applicantName required
Submit to /api/intake
Record response.completed
```

Those facts belong to Component, Definition, Form Runtime Actions, Mapping, or Ledger.

# 6. Form Runtime Actions

Form Runtime Actions captures what can happen inside the Formspec runtime.

This note previously used **Operations** as shorthand. A formal spec should use **Form Runtime Actions** or another non-WOS name because [WOS Kernel §11.3 Instance Operations](../../../work-spec/specs/kernel/spec.md#113-instance-operations) already owns operations for WorkflowProcess instances.

Form Runtime Actions runs entirely on the Formspec side of the IntakeHandoff seam ([ADR 0073](../../../thoughts/adr/0073-stack-case-initiation-and-intake-handoff.md) D-3). The corresponding post-handoff surface is WOS Kernel §11.3 Instance Operations; the two never overlap on the same lifecycle moment. FEL drives action preconditions; it is the cross-stack predicate language by [ADR 0075](../../../thoughts/adr/0075-rejection-register.md) I-2, so no second expression language is introduced.

The seam is:

```text
Form Runtime Actions
  owns: edit response, validate response, save draft, submit response,
        request local evidence, produce Intake Handoff

WOS Kernel Instance Operations
  owns: create workflow instance, accept intake handoff, process events,
        advance time, migrate, suspend, resume, terminate
```

It answers:

```text
What actions can be invoked?
Who or what actor context is each action designed for?
What preconditions apply?
What validation pass should run before action effects?
What effects occur?
Which submission policy runs?
What evidence artifacts may be produced?
What Respondent Ledger events are requested?
```

Form Runtime Actions is scoped to the Formspec runtime boundary: response editing, validation, save/submit actions, local evidence requests, and handoff production. It is not a workflow engine, case lifecycle model, adjudication model, notification system, or host authorization layer. Those concerns belong to the consuming application, WOS Kernel §11.3, Trellis custody/anchoring, or another workflow host.

Form Runtime Actions orchestrates effects. It does not own the internal body shape of artifacts produced by other specs.

Examples:

| Runtime concern | Correct owner |
|---|---|
| Action identity and intent | Form Runtime Actions |
| Action preconditions | Form Runtime Actions, using FEL |
| Field requiredness | Definition |
| Validation findings | Validation Report |
| External payload transformation | Mapping |
| Handoff envelope shape | Intake Handoff (cross-stack; see §3.2) |
| Respondent Ledger event semantics | Respondent Ledger — Formspec owns event semantics, Trellis Core §22 owns canonical admission (cross-stack; see §3.2) |
| Signature/custody policy | Posture Declaration (Trellis-owned; see §3.2) |
| Verification result evidence | Verification Receipt |

Form Runtime Actions should have enough structure to let a runtime invoke an action consistently, but not enough to redefine every downstream artifact. In particular, Form Runtime Actions *requests* Respondent Ledger events; it does not define their byte shape, hash obligations, or chain admission rules.

The important conceptual distinction is:

```text
Form Runtime Actions says: run this submission, require this evidence, request this Respondent Ledger event.
Other specs say: what the submission payload, evidence, and Respondent Ledger event actually look like.
```

# 7. Component and Theme

Component remains the concrete UI layer.

Component answers:

```text
Which component renders this item?
Which component realizes this Experience unit?
Which button triggers this runtime action?
How are children ordered?
Which widget is used?
```

Theme answers:

```text
What visual density, spacing, typography, color, and presentation defaults apply?
```

Experience should not become layout. Component should not become task semantics. Theme should not become validation policy.

A future Component spec can add references such as:

```text
unitRef
taskRefs
actionRef
conceptRefs
```

Those references let concrete UI remain traceable to abstract intent without moving intent into the component tree.

# 8. Trace Graph

Trace Graph is the generated accountability layer.

It answers:

```text
Which component renders which item?
Which unit collects which item?
Which action runs which submission?
Which submission uses which mapping?
Which handoff references which Response and Validation Report?
Which reference explains which target?
Which ledger event records which runtime action?
Which receipt verifies which signature against which posture?
```

Trace Graph should be generated from source and evidence artifacts. It should not be authored as a parallel model.

The graph enables four capabilities:

| Capability | Value |
|---|---|
| Backward trace | Reconstruct why an output or evidence artifact exists |
| Forward impact analysis | Preview what changes when a source artifact changes |
| Conformance coverage | Identify which relationships fixtures exercise |
| Pattern lookup | Help AI or authoring tools reuse known interaction shapes |

Trace Graph has a staleness problem if materialized. The source-of-truth read path should be query semantics over the current source and evidence artifacts. A materialized graph is an optional cache, not an authority.

If a materialized graph exists, it must carry input digests and processors must reject it as stale when any source input digest changes.

Until a named consumer needs it, Trace Graph should remain a conceptual accountability model rather than a required runtime artifact.

# 9. Primitive Vocabulary

This note should not introduce a new `formspec-foundations` package. Future companion specs need a small Formspec-domain reference vocabulary, but the general primitives already have stack owners.

| Formspec-domain primitive | Purpose | Why local |
|---|---|---|
| `DefinitionRef` | `{url, version}` Formspec Definition identity | Definition is a Formspec-domain artifact |
| `TypedRef` | `kind:identifier` cross-Formspec-artifact reference (e.g., `item:applicantName`, `action:submitApplication`) | Bound to Formspec's artifact taxonomy (Item, Action, Concept, Unit) |

Stack-wide primitives route through their existing homes:

- **Hash strings.** `algo:digest` producers live in [`stack-common-hash`](../../../stack-common/crates/stack-common-hash/) (`sha256_prefixed`) and route through [`integrity-canonical`](../../../integrity-stack/crates/integrity-canonical/). Formspec schemas validate the `^[A-Za-z0-9._:+-]+:.+$` shape structurally; they do not redefine the producer. The stack `deny.toml` forbids direct `sha2` imports outside `integrity-stack`.
- **Opaque cross-system references.** The `urn:wos:` grammar (`{tenant}_{family}_{uuidv7_base32}`) lives in [`stack-common-typeid`](../../../stack-common/crates/stack-common-typeid/). Formspec consumes; it does not redefine.

The rule is: define `DefinitionRef` and `TypedRef` only where a follow-on Formspec spec needs them, and map all hash and opaque-reference production to `stack-common` / `integrity-stack` first. If a Formspec-domain primitive becomes reusable across more than Formspec, migrate it up instead of fanning out copies.

# 10. Prior Art Absorbed

This approach absorbs useful discipline from XForms, UsiXML/CAMELEON, and XIML without copying any of them wholesale.

| Tradition | Useful discipline | Formspec landing zone |
|---|---|---|
| **XForms** | Model/view split, deterministic form behavior, validation, submission semantics | Definition and Form Runtime Actions |
| **UsiXML / CAMELEON** | Task / abstract UI / concrete UI / final UI ladder | Experience, Component, Theme |
| **XIML** | Cross-layer relations and traceability | Trace Graph |

The goal is not standards parity. The goal is to preserve the useful separation of concerns in a JSON-native architecture that fits Formspec's existing artifacts.

# 11. Design Commitments for Follow-On Specs

Future formal specs and schemas should preserve these commitments.

## 11.1 Keep Schemas Closed

Schemas should stay closed by default. Extension seams should be named, explicit, and governed through Registry-style `x-` extensions.

## 11.2 Keep Behavior Out of Presentation

Component and Theme may present and organize fields, but they must not override Definition behavior.

## 11.3 Keep Experience Abstract

Experience should capture task intent and abstract grouping. It should not encode concrete layout, widget choice, or host-specific workflow implementation.

## 11.4 Keep Form Runtime Actions Orchestrational

Form Runtime Actions may coordinate actions, submissions, validation passes, handoffs, receipts, and ledger requests at the Formspec runtime boundary. It must not redefine the body schemas owned by those artifacts, and it must not absorb workflow or case lifecycle authority.

## 11.5 Keep Mapping Responsible for Boundary Translation

Payload construction belongs in Mapping. Form Runtime Actions should reference mappings rather than inventing inline transformation shapes.

## 11.6 Keep Trace Generated

Trace Graph should be generated from source and evidence artifacts. It should not become an authored duplicate of relationships already owned elsewhere.

## 11.7 Separate Concept From Ratification

This note should guide the formal specs, but formal specs must be written separately. They need their own schema files, conformance fixtures, migration notes, processor obligations, and test gates.

Minimum fixture sketches:

```text
Experience: a unit references Definition items and actions, and grouping does not change validation.
Form Runtime Actions: an action runs validation, references Mapping, requests ledger evidence, and stops at IntakeHandoff.
Component binding: concrete nodes keep unitRef/taskRefs/actionRef anchors without owning their semantics.
Trace query/cache: current-source query returns the expected edges; a materialized cache with a changed input digest is rejected as stale.
```

# 12. Follow-On Spec Work

The next formalization pass should produce separate artifacts, in this order:

```text
1. Experience companion spec and schema, grounded by the wireframe generator use case
2. Form Runtime Actions companion spec and schema, with the WOS Kernel handoff seam explicit
3. Component reference additions
4. References typed-target migration, only where a named consumer needs it
5. Trace query/cache spec, only after a named consumer exists
6. Primitive vocabulary cleanup as local $defs or stack-common/integrity-stack reuse, not a new Formspec package
```

Each follow-on spec should include:

```text
normative document shape
JSON Schema
examples
semantic validation rules
conformance fixtures
generated type impacts
downstream consumer impacts
migration notes
```

This concept note should not carry those details. Its job is to make the architecture hard to misunderstand before the formal specs begin.

# 13. Open Questions

These questions should stay visible, but they should not block the conceptual direction.

## 13.1 Should primitives move above Formspec?

Already done for the general primitives. `HashString` production lives in [`stack-common-hash`](../../../stack-common/crates/stack-common-hash/) and routes through [`integrity-canonical`](../../../integrity-stack/crates/integrity-canonical/); the opaque `Ref` grammar lives in [`stack-common-typeid`](../../../stack-common/crates/stack-common-typeid/). Formspec should not start a local foundations package for those.

The remaining trigger to revisit is the inverse: if `DefinitionRef` or `TypedRef` turn out to be reusable across more than Formspec, migrate them up.

## 13.2 Should Trace Graph become a query model?

A query model is the source-of-truth answer. A materialized graph can exist as a cache only when it carries input digests and every consumer rejects stale cache entries.

The trigger to formalize this is demand: if several consumers need trace views, specify query semantics first and cache format second.

## 13.3 Should Form Runtime Actions be an overlay on Definition?

Form Runtime Actions can remain a peer artifact if it only orchestrates runtime actions. If it starts changing Definition behavior, it should become an explicit behavioral overlay with merge semantics or move into a future Definition v2 model.

The trigger to revisit this is leakage: if Form Runtime Actions repeatedly needs to suppress, override, or alter Definition semantics, the peer-artifact model is wrong.

## 13.4 How broad should TypedRef be at v1?

TypedRef should include only kinds that real consumers need. It can grow later, but every new kind should have clear semantics and conformance tests.

## 13.5 How should identity mappings become ergonomic?

Form Runtime Actions should keep payload kinds strict and rely on Mapping. If identity Mapping documents are too verbose, fix Mapping ergonomics rather than adding payload shortcuts to Form Runtime Actions.

---

# 14. Final Direction

Ship the concept:

```text
Experience           = abstract journey and task intent
Form Runtime Actions = form-scoped action and submission orchestration
Component            = concrete UI realization
Theme                = visual presentation
Mapping              = boundary translation
Trace Graph          = generated accountability and impact index
Primitive refs       = DefinitionRef/TypedRef only; hash/ref primitives stay in stack-common/integrity-stack
```

Do not ship this note as the formal spec.

Use it to guide the formal specs and schemas that come next. The formal artifacts should be narrower, more mechanical, and separately testable. This note should remain the doctrine: what belongs where, why the layers exist, and how Formspec becomes a semantic interaction contract instead of a pile of disconnected UI, validation, runtime, and audit documents.
